CommerceIQ · Extraction↗API crawler automation
Browser→REST API
~90% lower compute costs

A browser runs a whole page to reach its data. Many of our extraction workloads could retrieve the same underlying structured data through a REST service.

The change

I re-architected heavy browser-based crawlers as asynchronous REST extraction services. A worker waiting on a network response can yield while other requests make progress.

The outcome

Compute infrastructure costs for the affected workloads fell by approximately 90%. This figure measures extraction cost. The ingestion reliability and peak uptime figures describe separate production outcomes.

Operating under load

I profiled container CPU and memory on Kubernetes and investigated queue deadlocks across our cloud workloads. Resolving those bottlenecks helped sustain 99.9% crawler uptime during peak loads.

Personal project · In development↗CodeShare
Editor A⇄Room⇄Editor B
Room A collaborative editing

I’m building an editor where several people can work in one room. The design has to answer two questions: which edits belong together, and how does each server learn what changed?

Inside a room

The React editor connects to Spring Boot using STOMP over WebSockets. Room-scoped state keeps one editing session separate from another.

Across servers

Redis Pub/Sub carries edit events between instances. A subscriber can then deliver changes to connected clients in the relevant room.

Current status

Development is ongoing. A public demo will follow deployment.
